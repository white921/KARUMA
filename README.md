# LEVELIA Bot

`LEVELIA` の運用に合わせた Discord Bot です。Discord 固有 ID と表示文言は、LEVELIA の構成を参照します。

パネル設置は Bot 起動時の自動投稿ではなく、対応チャンネルで `/panel` を実行する運用です。

遊戯パネルのゲームパス（2週間・1か月）は、期間と料金を確認して「購入を確定」を押すと購入されます。「キャンセル」では料金は発生しません。ゲームパスを所持している場合は確認画面を表示せず、購入を拒否します。確定時にも所持状態を再確認し、有効なパスの追加購入・延長は行いません。

市場・宮廷市場・闇市場の商品購入、スパチャ、通常送金・カジノ送金のパネルでは、入力フォーム送信後に確認画面を表示します。商品名や送付先、金額、使用チケットなどを確認し、「購入を確定」または「送金を確定」を押した時点で決済します。キャンセル時は通貨・チケットを消費しません。確認画面は10分間有効で、Bot再起動後は入力からやり直してください。

## コード構成

`service`・`constant`・`type`・`command`・`util` を機能別フォルダーに分けています。
パネルの描画・設置は `src/panel`、イベントの振り分けは `src/handler` で管理します。
配置先と追加時のルールは [ソースコードの配置](src/README.md) を参照してください。

## メンバー一覧のキャッシュ

キャスト選択・スパチャ・ロール対象処理などのメンバー一覧は `GuildMemberCacheService` を共通で利用します。起動時に全件取得し、その後は discord.js が参加・退出・ロール・名前の変更通知をキャッシュに反映します。Select を開くたびに、このキャッシュから選択肢を作ります。定期的な全件再取得は行いません。

通常の再接続（RESUMED）ではキャッシュを維持し、新しいセッション（READY）やサーバー障害からの復旧時には再取得します。同時取得は1つにまとめ、全件取得の間隔は31秒以上空けます。初期化に失敗した場合は次の操作時に再試行し、未完成の一覧は使用しません。キャスト支払い・スパチャの確定時には、選択した対象者の在籍・ロールを個別に再確認します。

## 名前の重複判定

口座開設・面接・名前変更時の口座名の重複判定は、サーバーに在籍中の口座だけが対象です。退出した人の口座名は対象外となり、再参加すると自動で対象に戻ります。同名の口座がある場合にDiscordへ現在の在籍を確認するため、過去の退出者にも適用されます。在籍確認に失敗した場合は判定を中止します。

退出中に別の人が同じ名前を使い始めても、再参加時に自動改名はしません。以後の判定では在籍中の両方の口座が対象になります。退出時の残高・履歴の処理は変更しません。

## 個人への送金上限

同じ相手への月間送金上限は500,000 LIAです。送金元が「皇帝」「英傑」「支配人」「システム支配人」のいずれかのロールを持つ場合は、この上限を適用しません。コマンド・パネルの両方に適用し、受取側だけが対象ロールを持つ場合は免除しません。残高不足や不正な金額は従来どおり拒否します。

## 入出金DM通知

すべての通知Embedの本文末尾に、銀行パネルへ移動する「[取引履歴はこちら](https://discord.com/channels/1534636292153807039/1534648842719465683)」リンクを表示します。

対象取引の受取人全員に通知します。剥奪・減額は残高が減った本人に通知します。通常送金、GF・麻雀・その他の賭博送金、スパチャ、個別付与、剥奪、ロール別一括付与、給料、ブースト報酬、ルーレット配当・参加ボーナス、おみくじ（凶の減額を含む）、チケット換金が対象です。紋章支払いと購入代金は対象外です。VC報酬は別Botの既存通知を使用します。

送金・賭博送金・スパチャは送金者の表示名とアイコンを表示し、付与・剥奪・給料・報酬・換金はLEVELIA BOTの名前とアイコンで表示します。運営操作の実行者名はDMに表示せず、従来の運営ログに記録します。金額、処理直後の残高、任意の備考を表示し、備考が空なら省略、1,024文字を超える場合は末尾を省略します。

通知は取引確定後に1回試み、DM拒否などの失敗はログに残します。通知失敗による取消・再決済・再送はしません。給与はロールごとに1通、ルーレット配当は同じラウンドの当選分を受取人ごとに合算して1通にします。換金の処理済み確認では再通知しません。導入前の取引を遡って通知する機能はありません。

## 管理者の残高増減

皇帝・英傑・財務員・システム支配人は `/残高増減 ユーザー:@対象 増減額:1000 備考:報酬` で1,000 LIAを付与し、`増減額:-1000` で1,000 LIAを剥奪できます。備考は任意です。既存の管理者パネルと同じ付与・剥奪処理を使用し、付与原資を実行者や銀行Botの残高から引き落としません。個人送金の月間上限も適用されません。

0・口座未開設・残高を超える剥奪・サブアカウントへの付与は拒否します。操作は既存の取引履歴と付与・剥奪ログに記録され、結果は実行者だけに表示されます。

「増減ログ」スレッドには、プラスを「付与」、マイナスを「剥奪」として、実行者・対象者・金額・備考を記録します。

## システム支配人の権限

システム支配人（`ROLE_IDS.GIJUTU_LEADER`）は全コマンド・パネルの操作権限を持ちます。新しい操作権限チェックには `src/util/shared/operatorPermission.ts` の `hasOperatorRole` を使い、システム支配人を許可します。`hasRole` は対象者の属性・料金・所有ロールを調べる関数として維持します。

金額・残高・口座・チケット・処理状態などの整合性チェックは適用します。停止中の機能は再開せず、権限による利用制限を免除します。遊戯は旅人以上の通常料金、独房は該当する罪の料金（罪ロールがなければ空位者と同じ料金）を使います。

## 任意環境変数

- `TECHNICIAN_IDS`
  - カンマ区切りの Discord ユーザー ID
- `RAILWAY_PROJECT_TOKEN`
  - Railway の定期再デプロイ機能を使う場合に必要
- `REGISTER_COMMANDS_ON_BOOT`
  - `true` のときだけ Bot 起動時にコマンド再登録を実行
  - 通常は `false` のままにして、必要時だけ `npm run register` を使う
- `EXPIRED_VC_CHECK_INTERVAL_MS`
  - ホテルVCの期限切れチェック間隔
  - デフォルトは `60000` ミリ秒
- `ENABLE_SCHEDULES`
  - `false` のとき Bot 起動時に cron/schedule 系の処理を開始しない
  - 将来 worker service へ定期処理を逃がすときに main Bot 側で `false` にする
- `ENABLE_EXPIRED_VC_CHECKER`
  - `false` のとき ホテルVC期限切れチェックを開始しない
  - 将来 worker service 側だけで期限切れチェックを動かすときに使う
- `MYSQL_CONNECTION_LIMIT`
  - MySQL connection pool の最大接続数
  - デフォルトは `5`
- `MYSQL_SLOW_ACQUIRE_LOG_MS`
  - DB接続取得待ちがこのミリ秒以上になったら警告ログを出す
  - デフォルトは `1000`
- `ROULETTE_2ND_PANEL_CHANNEL_ID`
  - ヨーロピアンルーレット第2部パネルを置くTCのID
- `ROULETTE_3RD_PANEL_CHANNEL_ID`
  - ヨーロピアンルーレット第3部パネルを置くTCのID
- `BOT_HEALTH_CHECK_INTERVAL_MS`
  - Bot健全性監視の実行間隔
  - デフォルトは `15000` ミリ秒
- `BOT_HEALTH_ACK_TIMEOUT_MS`
  - interaction受信後にACK完了を待つ最大時間
  - デフォルトは `30000` ミリ秒
- `BOT_HEALTH_HANDLER_TIMEOUT_MS`
  - interaction のACK後、処理完了を待つ最大時間
  - デフォルトは `45000` ミリ秒
- `BOT_HEALTH_GATEWAY_DISCONNECT_TIMEOUT_MS`
  - gateway切断後に自己再起動するまでの猶予
  - デフォルトは `300000` ミリ秒
- `BOT_HEALTH_MAX_CONSECUTIVE_ACK_FAILURES`
  - 連続ACK失敗で自己再起動するしきい値
  - デフォルトは `3`
- `EVALUATION_ARCHIVE_R2_ENDPOINT`
  - 評価シートHTMLを保存するCloudflare R2のS3 APIエンドポイント
- `EVALUATION_ARCHIVE_R2_ACCESS_KEY_ID` / `EVALUATION_ARCHIVE_R2_SECRET_ACCESS_KEY`
  - 上記バケットに限定した「Object Read & Write」権限のR2 APIトークン
- `EVALUATION_ARCHIVE_R2_BUCKET`
  - 評価シートHTMLを保存するR2バケット名
- `EVALUATION_ARCHIVE_PUBLIC_BASE_URL`
  - 公開バケットのURL（末尾の`/`なし）。本番ではカスタムドメインを使用する

`RAILWAY_DEPLOYMENT_ID` は Railway の組み込み環境変数をそのまま利用します。

## 市場ガチャ

市場パネルで「市場ガチャを引く」を押すと、5,000LIAまたは招待ポイント1ptを選択できます。支払い方法を選んだ後、確認ボタンを押すと抽選します。2種類の抽選を合計して日本時間で1日5回までです。技術統括・鯖主を含め、ロールによる回数制限の例外はありません。

`/招待ポイント追加 ユーザー ポイント` でユーザーの招待ポイントを追加できます。実行できるのは技術統括・鯖主・管理者・ショップリーダー・ショップ従業員です。ポイントの付与・消費履歴はDBに保存されます。

コマンドでの付与成功時は「ガチャポイント付与ログ」スレッド（`1551228490374971532`）にも、付与者・対象者・付与ポイント・付与後残高・日時をEmbedで記録します。導入後の付与のみが対象で、過去分の転記は行いません。Discordへのログ送信に失敗しても付与は取り消さず、Botのエラーログに記録します。

- シークレット無料チケット・フリーダム無料チケット：当選時に自動付与され、次回該当ホテルを選ぶと優先して消費される。シークレットは1枚（6.5%）または3枚（4%）、フリーダムは1枚（4%）が当選する
- 遊戯チケット：遊戯VC作成用。市場ガチャで1枚（12.5%）または3枚（7.5%）が当選し、所持している場合はゲームパネルから24時間の遊戯VCを1部屋無料で作成できる
- 市場割引券：市場ガチャで5%OFF（5%）・10%OFF（2%）が自動付与される。利用時は総合お問い合わせで市場チケットを切り、商人に割引後の支払額を確認してから、その金額を市場パネルで送金する。100万LIA以上の商品には利用できない
- アイドルコラボ・サプボ指名・どこでも通行券・カスタムロール（1週間）：利用時は[総合お問い合わせ](https://discord.com/channels/1534636292153807039/1534641084016230600)で市場チケットを切り、当選メッセージを提示する。アイドルコラボとサプボ指名は対象ロールを当選案内でメンションする
- ワンモアチャンス：招待ポイントを1pt自動付与し、そのポイントで市場ガチャを引ける。1日休み：その日の以後の市場ガチャを停止する
- サプボ・歌みた：R2の公開URLと録音者をDBから選び、当選案内とDMで実際の録音者をメンションしてURLを渡す。Discordの添付容量上限を受けない
- 音源テーブルと配信履歴により、誰のどのファイルを渡したかを抽選ごとに記録する

既存DBに導入する場合は、デプロイ前に `src/sql/20260713_market_gacha.sql`、`src/sql/20260714_market_gacha_audio.sql`、`src/sql/20260718_shop_tickets.sql`、`src/sql/20260716_invite_points.sql`、`src/sql/20260716_market_gacha_audio_correction.sql`、`src/sql/20260727_game_free_tickets.sql`、`src/sql/20260727_item_inventory.sql`、`src/sql/20260901_game_vc.sql`、`src/sql/20260902_market_gacha_update.sql`、`src/sql/20260906_market_gacha_scarlet_mention.sql`、`src/sql/20260911_market_gacha_killer_audio.sql`、`src/sql/20260913_market_gacha_superchat_audio.sql`、`src/sql/20260913_market_gacha_tsuyogari_audio_correction.sql`、`src/sql/20260919_market_gacha_audio.sql`、`src/sql/20260924_market_gacha_audio.sql` をこの順で適用してください。新規DBでは `src/sql/createTable.sql` に含まれています。既存の3券種テーブルは移行確認のため残し、Botは `items` と `item_users` を参照します。適用後、技術統括が市場パネルのチャンネルで `/panel` を実行してパネルを更新してください。

## 評価期限の毎日通知

毎日 **23:00（日本時間）** に「判定官チャット」(`1547130596873216081`) へ、判定官・侍従ロールと期限直前の旅人をメンションします。「2日前」は翌々日、「1日前」は翌日が期限の人です。現在在籍する旅人だけを対象とし、4フォーラムのシートをユーザーID単位にまとめます。Discordでアーカイブされたスレッドも取得します。

期限はDiscordの最新スレッド名から読み取り、DBの現在スレッド対応と照合します。4枚の欠落・期限不一致などは推測せず対象者を除外して `[EvaluationReminder] 要確認の評価シート` をログに記録します。月日表記による翌年の誤通知を避けるため、作成から365日以上経過したシートも要確認にします。片方が0人なら「該当者なし」、両方0人なら投稿しません。通常は1投稿で、2000文字を超える場合は分割し、判定官・侍従ロールの通知は最初の投稿だけにします。

既存DBにはデプロイ前に `src/sql/20260922_evaluation_deadline_reminders.sql` を適用してください。通知日・本文・送信済みIDを保存し、起動時と23時台の5分ごとに未完了分を再試行します。送信後のDB更新が失敗した場合は、当日23時以降のBot投稿を確認して重複を避けます。23時台を通して停止していた日の通知は翌日に持ち越しません。`ENABLE_SCHEDULES=false` では動作しません。

送信先ではBotに「チャンネルを見る」「メッセージを送信」「メッセージ履歴を読む」が必要です。判定官・侍従ロールが誰でもメンション可能でない場合は「@everyone、@here、すべてのロールにメンション」の権限も必要です。

## 評価シートの保存・削除・復元

`/2評価シート` で作成した4つの評価スレッドは、対象DiscordユーザーIDとともにDBへ記録されます。既存DBにはデプロイ前に `src/sql/20260715_evaluation_sheet_archives.sql` と `src/sql/20260715_evaluation_sheet_current_threads.sql` をこの順で適用してください（新規DBでは `src/sql/createTable.sql` に含まれます）。評価シートの保存・削除を使う前に、Cloudflare R2の公開バケットと以下のR2環境変数も設定してください。

評価本文を保存するため、Discord Developer Portal の Bot 設定で **Message Content Intent** も有効にしてください。コード側でも同Intentを要求しています。有効化せずに起動するとDiscordが接続を拒否します。

評価フォーラムではBotに「チャンネルを見る」「メッセージ履歴を読む」「スレッドの管理」「ファイルを添付」の権限も必要です。

- `/評価シート保存削除 user_id:<DiscordユーザーID> reason:<任意>`: 4スレッドの内容をHTMLとしてMySQLへ保存してから削除する。対象者が脱退済みでも実行できる
- `/評価シート復元 user:@ユーザー`: どのカテゴリでも実行できる。新しい評価スレッド4件を作成・DB登録し、それぞれに対応する直近の過去評価HTMLを添付する
- 保存・削除・復元を実行できるのは、システム管理・皇帝・判定官統括・英傑のみ

通常の `/2評価シート` で作成した場合も、過去評価があれば自動で添付されます。HTMLには投稿者のDiscordアイコン、サーバー表示名、ユーザー名、日時を記録します。

復元時は各フォーラムの直近アーカイブ1件を、固有ファイル名で添付します。全アーカイブは同時にCloudflare R2へHTMLファイルとして保存され、次回保存時に過去評価HTMLへの添付はR2の固定URLリンクへ置き換えられます。そのため、元スレッド削除後もHTML内の過去評価リンクは切れません。

R2は公開バケットとして設定します。評価内容をURLを知る人に見せてもよい運用であることを確認してください。CloudflareではR2バケットにカスタムドメインを接続して公開し、開発用の`r2.dev` URLは本番用途に使わないでください。

保存に失敗した場合はスレッドを削除しません。保存後に削除だけ失敗した場合も、再実行すれば再保存せず削除を再試行します。

現在の評価スレッドは `user_id + forum_id` を主キーとして管理します。同じユーザーが再度仮メンになった場合、作成された新しいスレッドIDでその行を更新します。過去のスレッドIDと評価本文はアーカイブとして保持されます。

## ヨーロピアンルーレット（2026-07-17）

ルーレット用テーブルを作成するため、デプロイ前に `src/sql/createTable.sql` を対象のMySQLへ適用してください。第1部〜第3部のパネル設置先は環境変数で指定します。運用開始前に対応するTCを作成し、環境変数を設定してください。

各パネルTCで技術統括が `/panel` を実行すると、その部に対応したパネルを設置できます。参加者は「賭けを開始する」から賭け方と金額を選び、確認画面で確定します。一つのラウンドで確定できるベットは一人一件だけです。

- 第1部: 赤・黒・偶数・奇数（2倍）
- 第2部: 第1部にダズン `1-12` / `13-24` / `25-36`（3倍）を追加
- 第3部: 第2部にストレートアップ（36倍）と任意の二数字によるスプリット（18倍）を追加
- `0` の場合は全ベットが没収されます

運営コマンドを実行できるのは、イベント統括またはイベントスタッフのロール所持者だけです。以下の順で運用します。

1. `/賭け開始 fase:1st|2nd|3rd` で、開催する部を指定して受付を開始する。
2. 必要なら `/賭け終了` で明示的に締め切る。`/結果` は受付中でも自動的に締め切って精算する。
3. ディーラーが `/結果 number:0〜36` を実行する。結果と当選・配当は実行チャンネルへ投稿され、通貨残高と取引履歴が同時に更新される。
4. 次のラウンドは、前の結果を確定した後に再び `/賭け開始` を実行する。第1部・第2部を2回ずつ行う場合も同様です。
5. 終了時に `/ボーナス付与` を一度実行すると、そのイベントで一度でも確定ベットした参加者へ30,000通貨を配布する。二重配布はされません。

参加者が受付中ではない部の「賭けを開始する」ボタンを押した場合は、賭け方の選択画面を開かず、受付開始前である旨を本人だけに表示します。

### 銀行窓口の取引履歴

取引履歴で、取引相手・アクションの種類（複数選択）・収入／支出を組み合わせて絞り込めます。
種類は本人の履歴にあるものだけ表示し、GF・麻雀・その他の送金は「カジノ」にまとめます。
市場での通常購入・闇市場購入・専用市場購入・市場ガチャ・スタンプ支払い・チケット換金・名前変更は「市場・夢印」にまとめます。
通常の送金とスパチャは「送金」、ロール別送金・付与・剥奪は「付与・剥奪」にまとめます。
ホテル・日記・遊戯の間・ルーレットも施設ごとにまとめ、履歴本文には個別の取引名を表示します。
条件間はAND、複数選択した種類はORです。条件を変更すると1ページ目へ戻り、ページ移動では条件を維持します。
選択解除または「条件をすべて解除」で絞り込みを解除できます。該当0件でも条件を変更できます。
収入／支出は本人の残高の増減で判定し、増減0の取引は「すべて」で表示します。
付与・剥奪・報酬の取引相手は表示と同じBotとして扱い、操作した管理者の収支には含めません。
